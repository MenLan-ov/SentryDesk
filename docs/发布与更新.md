# 发布与自动更新

本文说明如何把一次改动发布成**能被应用内「检查更新」拉取**的新版本。
它不是「构建成功就完事」的说明——本项目的四轮安装失败排障（v0.8.4 → v0.8.7）证明，
安装包从构建到用户装好之间，还有签名、权限、杀软、资产上传四个环节会单独出错。

> **现状**：应用内更新端点为
> `https://github.com/MenLan-ov/SentryDesk/releases/latest/download/latest.json`
>
> ⚠️ **私有仓库的 Release 资产无法匿名下载**。仓库必须设为 Public，自动更新才能在评委/用户机器上生效。
> 若保持 Private，「检查更新」会走降级分支，提示「可直接用新版安装包覆盖安装」——功能不崩，但更新不可用。

---

## 一、为什么需要两套签名

| 签名 | 用途 | 产物 | 丢了会怎样 |
|---|---|---|---|
| **Authenticode**（自签名证书）| 让 Windows 显示发布者、通过 UAC 校验 | exe 内的签名 | UAC 弹「未知发布者」，用户不敢装 |
| **minisign**（`tauri signer`）| 让 `tauri-plugin-updater` 校验更新包完整性 | `.sig` 文件 | 自动更新拒绝安装，报签名不匹配 |

两者互相独立：前者防「来源不明」，后者防「更新包被篡改」。**缺任一个都会在真实用户机上出问题。**

| 物料 | 位置 | 是否进仓库 |
|---|---|---|
| 签名证书 | `_tools/sign/SentryDesk.cer`（指纹 `ACE77E8E…`，有效期至 2031-11-11）| 是（公钥部分）|
| 更新私钥 | `_tools/sign/updater.key` | **否**，已在 `.gitignore` |
| 更新公钥 | `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey` | 是 |

> 私钥泄露等于任何人都能给你的用户推更新包。本项目在 `_tools/sign/` 下同时放了 `updater.key.pub` 便于核对，私钥只在本机。

## 二、发版流程

### 2.1 改版本号（四处必须一致）

| 文件 | 字段 |
|---|---|
| `package.json` | `version` |
| `src-tauri/Cargo.toml` | `[package] version` |
| `src-tauri/tauri.conf.json` | `version` |
| `src/version.ts` | `APP_VERSION` |

前三个是构建系统读的，第四个是界面顶栏与关于页读的。**漏改第四个会出现「装的是新版、顶栏显示旧版」**——
v1.0.5 发布时就真踩过这个坑（桌面残留旧 exe 导致永远显示 v0.7.6），所以这条单列出来。

### 2.2 构建（带更新签名私钥）

```bash
# 私钥只在本机，不进仓库
export TAURI_SIGNING_PRIVATE_KEY="$(cat ../_tools/sign/updater.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""

pnpm run build                  # 前端产物
npx tauri build --bundles nsis  # 产出 setup.exe + .sig
```

### 2.3 签 Authenticode（主程序 + 安装包）

```bash
# 用批处理更稳，避免手打 40 位指纹出错
_tools\sign\sign.bat src-tauri\target\release\sentrydesk.exe
```

**顺序很重要**：必须先签 exe，再用已签的 exe 重打安装包，最后签安装包本体。
如果先打包装再签 exe，安装包里装的还是未签名版本。

```bash
cd src-tauri\target\release\nsis\x64
makensis -INPUTCHARSET UTF8 installer.nsi
copy nsis-output.exe ..\..\bundle\nsis\SentryDesk_<版本>_x64-setup.exe
```

### 2.4 重签更新签名（最容易漏的一步）

安装包被 signtool 改写过，字节变了，**之前的 `.sig` 立即失效**。必须重签：

```bash
echo "" | npx tauri signer sign --private-key-path ..\..\_tools\sign\updater.key ^
  ..\..\bundle\nsis\SentryDesk_<版本>_x64-setup.exe
```

> 这一步漏了，用户点「检查更新」会下载成功但安装失败，且错误信息指向签名不匹配——
> 看起来像网络问题，实际是自己漏签。

### 2.5 便携版（可选）

Windows 资源管理器「发送到 → 压缩文件夹」会按 GBK 写中文文件名，解压后变乱码
（实际出现过 `õ¢+þö¿Þ»¦µÄ.txt` 这种）。必须用 Python 的 `zipfile`：

```python
import zipfile, os
with zipfile.ZipFile("SentryDesk_<版本>_portable.zip", "w", zipfile.ZIP_DEFLATED) as z:
    for root, _, files in os.walk("stage"):
        for f in files:
            p = os.path.join(root, f)
            z.write(p, os.path.relpath(p, "stage"))
```

仓库里已有现成脚本 `_tools/pack/make_portable.py`，不用手写。

## 三、Release 资产与 latest.json

一次 Release 需要上传四个资产：

| 资产 | 说明 | 大小参考 |
|---|---|---|
| `SentryDesk_<版本>_x64-setup.exe` | 安装包（含 Authenticode 签名）| 4.11 MB（v1.0.5）|
| `SentryDesk_<版本>_x64-setup.exe.sig` | 更新签名 | 约 400 B |
| `SentryDesk_<版本>_portable.zip` | 便携版（可选）| 约 4.0 MB |
| `latest.json` | 更新清单 | 约 700 B |

`latest.json` 模板（`signature` 填 `.sig` 文件的**完整内容**，不是路径）：

```json
{
  "version": "1.0.5",
  "notes": "参赛版：种子情报库首启导入 2979 条、首启引导、学习报告 PNG、安装目录自选、检查更新。",
  "pub_date": "2026-11-11T16:25:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<.sig 文件的全部内容>",
      "url": "https://github.com/MenLan-ov/SentryDesk/releases/download/v1.0.5/SentryDesk_1.0.5_x64-setup.exe"
    }
  }
}
```

发布后的固定地址：
`https://github.com/MenLan-ov/SentryDesk/releases/latest/download/latest.json`

仓库里有 `_tools/pack/make_release.py` 负责生成这份清单，避免手填 signature 出错。

## 四、证书导入（解决「未知发布者」）

自签名证书未导入时，UAC 会显示「未知发布者」。导入一次即可：

```bat
certutil -addstore -user -f Root              _tools\sign\SentryDesk.cer
certutil -addstore -user -f TrustedPublisher  _tools\sign\SentryDesk.cer
```

或用 `_tools/sign/导入证书.bat`（带说明与卸载指引，交互式）。

> **非交互环境（脚本/CI）里 `Import-Certificate` 会报「此操作中不允许使用 UI」**，
> 必须用 `certutil` + `-f` 静默导入。这条踩过，写死在这里。

## 五、CI 三道关

`.github/workflows/ci.yml` 三个作业，任何一道红都不该发版：

| 作业 | 运行环境 | 命令 | 拦什么 |
|---|---|---|---|
| 前端 | windows-latest | `vue-tsc --noEmit` + `pnpm build` | 类型错误、构建失败 |
| 后端 | windows-latest | `cargo test --locked` + `cargo clippy -- -D warnings` | 单测失败、任何 clippy 警告 |
| 内容 | ubuntu-latest | `python _tools/ci/check_knowledge.py` | 知识库字段缺失、答案越界、路径引用失效 |

内容校验是本项目特有的一道关——教学内容是 JSON，写错一个字段不会报编译错，只会让某张卡打不开。
当前校验输出：**110 卡 / 338 题 / 91 术语 / 14 路径，全部通过**。

## 六、发布检查清单

发版前逐项打勾，任何一项不确定就别发：

- [ ] 四处版本号一致（`package.json` / `Cargo.toml` / `tauri.conf.json` / `src/version.ts`）
- [ ] `cargo test` 全过（当前 40 个单测）
- [ ] `vue-tsc --noEmit` 零错误
- [ ] `cargo clippy -- -D warnings` 零警告
- [ ] `python _tools/ci/check_knowledge.py` 通过
- [ ] 安装包 Authenticode 验证为 `Valid`（`signtool verify /pa`）
- [ ] `.sig` 与安装包**同一次构建**（覆盖过 exe 就必须重签）
- [ ] `latest.json` 的 `version` 高于线上已发布版本
- [ ] 仓库为 **Public**（否则自动更新不可用）
- [ ] 真机跑一遍：安装 → 打开 → 情报页有数据 → 学一张卡 → 做一道题
- [ ] **只发 `setup.exe` 与 `portable.zip`，不投放裸 exe**

> 最后一条是血泪教训：桌面上残留的单文件旧 exe 内嵌旧内容，双击它永远显示旧版本号与旧内容，
> 会让人误判「新版没生效」。发布纪律比技术方案更能防这类问题。
