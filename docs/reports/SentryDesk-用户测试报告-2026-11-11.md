# SentryDesk 用户视角测试报告

> 测试时间：2026-11-11 09:41–10:25 ｜ 被测版本：v0.6.0（10:05 / 10:13 / 10:19 三次构建）
> 测试方式：以真实用户身份在成品 exe 上操作（UI 自动化驱动 + 数据库交叉核对），不做白盒假设
> 结论：**发现 11 个问题，其中 3 个阻断功能。全部 P0/P1 已修复并复测通过。**
> 附带最重要的一个结果：**采集功能此前完全不可用，本次修复后 5 个源全部成功、新增 56 条**

## 1. 测试思路

不当"点按钮的机器人"，而是模拟四类真实用户行为：

| 类型 | 具体做法 | 举例 |
|---|---|---|
| 正常操作 | 按产品设计路径走完整流程 | 搜索 → 看详情 → 写笔记 → 导出 → 采集 → 看板 |
| 边界操作 | 极限尺寸、空数据、首启动、极长输入 | 1024×680 最小窗口、删库重启、5000 字符搜索 |
| 错误操作 | 输错路径、空提交、重复点击 | 恢复不存在的备份、未作答提交自测、采集连点 |
| 匪夷所思 | 正常人不会这么干，但一定会有人这么干 | 搜 `%`、搜 `_`、搜 `' OR 1=1 --`、搜 emoji、搜 5000 个 A |

每条 UI 结论都与数据库实际状态交叉核对（`items` / `notes` / `collect_log` / `lesson_progress` 直查），避免"界面说成功、实际没写进去"。

## 2. 缺陷清单

### P0-1 笔记保存必失败（阻断）

- **现象**：给任何一条**还没有笔记**的情报写笔记，点保存后弹红字 `数据库错误：Wrong number of parameters passed to query. Got 3, needed 2`，内容不落库。
- **复现**：情报页 → 任选条目 → 笔记框输入 → 保存。
- **根因**：`db/repo.rs::upsert_note()` 的 INSERT 写成 `VALUES (?1, ?2, ?2, ?2)`（2 个占位符），却传了 3 个参数 `item_id, body, now`。已有笔记的条目走 UPDATE 分支所以侥幸正常，**新条目 100% 失败**。
- **修复**：改为 `VALUES (?1, ?2, ?3, ?3)`。
- **验证**：修复后保存提示"已保存"，`notes` 表新增 `(id=2, item_id=66, body=notesavetest)`。

### P0-2 采集全流程失效（阻断，最严重）

- **现象**：点"开始合规采集"，跑 25 秒，界面只显示"采集完成 +0 / 0 条"，**一条也没入库**；采集日志里查不到任何记录，无从判断原因。
- **根因**：`db/schema.rs::write_tx()` 先手动 `execute_batch("BEGIN IMMEDIATE")`，又调用 `Transaction::new_unchecked(conn, Immediate)` —— 后者**自身也会发 BEGIN**，于是变成"事务里再开事务"，SQLite 直接报 `cannot start a transaction within a transaction`。5 个源批量入库全部在第一步就崩。
- **影响面**：这是产品的核心卖点功能。现有 530 条数据是旧版本留下的，**当前版本装到评委机器上会"能看不能采"**。
- **修复**：去掉手动 BEGIN，只用 `Transaction::new_unchecked`。
- **验证**：修复后同一次点击，5 个源全部 `HTTP 200 / ok=1`，`items` 从 530 → 586（新增 56 条，去重正常），采样耗时 NVD 2.7s / GHSA 1.3s / KEV 3.0s / CISA News 0.3s / NCSC 2.2s。

### P0-3 采集失败不留任何证据（阻断排障）

- **现象**：P0-2 发生时，`collect_log` 一行都不写，界面上也没有原因。用户只能看到"+0 条"。
- **根因**：`cmd/collect.rs` 的 `Err` 分支只往 `details` 里塞 message 并计数，从不调用 `log_collect`；而 `details` 在 UI 上没有任何展示位。
- **修复**：`Err` 分支补写 `collect_log`（含错误原文）；前端监听 `collect://done`，失败时弹出"x ok / y failed + 第一条原因"。
- **验证**：正是这条补丁让 P0-2 的真实错误文本（`cannot start a transaction...`）暴露出来，否则这个问题会一直查不到。

### P1-4 采集 20 秒零反馈

- **现象**：点击采集后只有状态栏一个"采集中"字样，5 个源、20 多秒里完全不知道在干什么，也不知道卡在哪。
- **根因**：后端逐源 `emit("collect://progress")`，**前端从未 `listen`**（`grep listen(` 在 src/ 下零结果），事件发了个寂寞。
- **修复**：`store.ts` 新增 `initCollectEvents()`，`StatusBar` 显示"采集中 2/5 · CISA KEV"。
- **验证**：采样到完整序列 `0/5 NVD → 1/5 GHSA → 2/5 CISA KEV → 4/5 NCSC → 就绪`。

### P1-5 导出备忘写到"不知道哪里"

- **现象**：点"导出备忘"，提示 `已导出 → sentrydesk-memo-2026-11-11.md`，只给文件名。文件其实写在**进程当前工作目录**——装到 `Program Files` 时该目录不可写，导出会直接失败。
- **根因**：`cmd/export.rs` 直接用传入的相对路径 `std::fs::write(&path, md)`；对照之下，学习报告导出（`learn.rs`）早已正确地落到数据目录。
- **修复**：新增 `resolve_out_path()`，相对路径统一落到 app_data_dir，返回绝对路径；前端改用返回值回显。
- **验证**：提示变为 `已导出 → C:\Users\17638\AppData\Roaming\com.sentrydesk.app\sentrydesk-memo-2026-11-11.md`，文件存在且内容正确（2 条含笔记条目）。

### P1-6 搜索里的 `%` 和 `_` 被当通配符

- **现象**：搜 `%` 返回全部 530 条，搜 `_` 也是 530 条；搜 `100%`、`user_id` 这类词结果全部失真。
- **根因**：短词（<3 字符）走 LIKE 兜底时，直接把用户输入拼进 `%{q}%`，没有转义。参数化能防注入，但防不住通配符语义。
- **修复**：新增 `like_escape()`，四处 LIKE 统一加 `ESCAPE '\'`。
- **验证**：`%` → 2 条、`_` → 60 条，与库内 `instr()` 精确统计一致（修复前均为 530）。

### P2-7 切视图后搜索词"残留但不生效"

- **现象**：在情报页搜 `zzzznotexist`，切到学习/错题/设置，搜索框里还留着这个词，但列表完全没按它过滤——用户会以为"这软件搜索坏了"。
- **修复**：切换视图时把当前关键词重新应用到该视图的数据源；看板/错题/设置三页直接隐藏搜索框（那里搜索本来无意义）。

### P2-8 合规页展示的 UA 是假的

- **现象**：设置 → 合规，展示 `SentryDesk/0.1 (personal local research tool; contact: 17638@example.com)`。版本号停在 0.1，联系邮箱是 `example.com` 占位符，**前缀还正好是本机用户名**。
- **修复**：改为 `SentryDesk/0.6 (local personal research tool; non-commercial, robots-compliant)`。
- **理由**：合规页是给评委看的地方，一个假邮箱 + 过期版本号会直接削弱"合规采集"的可信度。

### P3-9 学习报告导出文案指错目录

提示"已导出到程序目录"，实际写的是数据目录。已改为回显绝对路径。

### P3-10 三张卡的 id 与 CWE 编号不一致（未修）

`more_cwe.json` 中：`cwe-352-x` 标 CWE-384（会话固定）、`cwe-434-x` 标 CWE-29（压缩包路径穿越）、`cwe-601-x` 标 CWE-1021-x（点击劫持）。**只影响命名可读性，不影响功能**（教学卡与情报库的关联走 `cwe` 字段）。考虑到 `paths.json` / `glossary.json` 有外部引用，改动风险大于收益，建议**只记录不改**。

### P3-11 英文文案 "107 topics · of 107"（未修）

中文本是"107 个主题 · 共 107"，英文直译成了别扭的 "· of 107"。建议改为 "107 topics · 107 total"。
